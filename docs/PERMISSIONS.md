# Prove2Break — Android Permissions

| Permission | Why Needed | When Requested | What Happens If Denied | Alternative Behavior |
|---|---|---|---|---|
| **Storage / File picker access** (`READ_MEDIA_*` or Storage Access Framework, no broad storage permission needed on modern Android) | To let the student pick a PDF file to upload as study material. | When the student taps "Add Material" and the file picker is invoked (SAF-based pickers on modern Android typically need no dangerous permission at all — noted here for completeness on older API levels). | The student cannot select a file to upload. | Student is shown a message explaining upload requires selecting a file; can retry the picker. |
| **Usage Access** (`PACKAGE_USAGE_STATS`, special app-ops permission via system settings) | To detect which app is currently in the foreground so restricted apps can be intercepted during focus. | Right before the student first sets up app restriction, with an explainer screen (`APP-RESTRICTION.md`). | App restriction/blocking does not function — restricted apps remain freely accessible. | Focus timer, breaks, quiz, and analytics all continue to work fully; the app clearly indicates restriction is inactive rather than silently failing. |
| **Accessibility Service** (only if adopted — see `APP-RESTRICTION.md`) | More immediate detection of foreground app changes than `UsageStatsManager` polling allows, if testing shows polling latency is a problem. | Only if/when this mechanism is adopted, with a dedicated explainer screen describing exactly what the service observes (window state, not content) and why. | Same as Usage Access denial — restriction inactive, rest of app unaffected. | Falls back to `UsageStatsManager`-based detection if available and granted. |
| **Notifications** (`POST_NOTIFICATIONS`, Android 13+) | To show break-available, session-complete, quiz-result, and other status notifications, and the required ongoing focus-session notification. | Just before the student starts their first focus session (contextual, not at cold launch). | No visible notifications; the ongoing foreground-service notification may still be constrained by system behavior without this permission on Android 13+. | Student is told notifications are off and can enable them later in Settings; timer/restriction/quiz still function, just without proactive alerts. |
| **Foreground Service** (`FOREGROUND_SERVICE`, plus the specific foreground service type declared in the manifest) | To keep the focus timer and restriction detection running reliably while the app is backgrounded. | Not user-facing (manifest-declared, granted at install for normal foreground service types); no runtime prompt for the base permission itself. | N/A — this is a normal permission, not a runtime-revocable one for standard foreground service types. | N/A |
| **Internet** (`INTERNET`) | Required for all backend communication: auth, upload, processing, quiz generation, analytics sync. | Not user-facing (normal permission, granted at install). | N/A. | Offline-capable features (timer, restriction, cached data) still work per `OFFLINE-MODE.md`; network-dependent features show a clear "needs connection" state. |

Every sensitive/special permission above is preceded by an in-app explainer screen stating plainly: what the permission does, exactly why Prove2Break needs it, and what still works if the student says no. No permission is requested at cold app launch "just in case" — each is requested contextually, immediately before the feature that needs it is used.

## Phase 8 QA Audit (2026-09-29)

Verified against `AndroidManifest.xml` and the actual runtime-request code:

- Manifest declares exactly the permissions this table lists: `INTERNET`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC` (matching `FocusService`'s declared `foregroundServiceType="dataSync"`), and `PACKAGE_USAGE_STATS` (`tools:ignore="ProtectedPermissions"`, correctly non-requestable via a runtime dialog).
- `UsageAccessHelper.hasUsageAccess()` (`app/src/main/java/com/prove2break/apprestriction/UsageAccessHelper.kt`) is checked defensively wherever restriction logic runs; `AppRestrictionMonitor.checkOnce()` simply `return`s early if access isn't granted — confirmed no crash path, restriction silently no-ops as documented while the rest of the app (timer/breaks/quiz/analytics) is untouched.
- `PermissionRationaleScreen.kt` shows the honest-limitations disclosure card before either permission card, and gates the `POST_NOTIFICATIONS` runtime request behind `viewModel.requiresNotificationRuntimePermission` (SDK 33+ only) — matches the table's "contextual, not cold-launch" requirement.
- **Minor doc/code timing mismatch found**: this table says notifications are "requested just before the student starts their first focus session," but the actual request happens on the **App Restriction setup** screen (`PermissionRationaleScreen`, Phase 3), before app-selection — not tied to the first focus session start. Functionally equivalent (still contextual, still before the ongoing-session notification would be needed, still not cold-launch), just a wording inaccuracy in this doc rather than a code bug. Leaving as a known documentation imprecision rather than changing the flow.
