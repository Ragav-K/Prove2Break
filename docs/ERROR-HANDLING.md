# Prove2Break — Error Handling

| Scenario | User-Facing Message Approach | Technical Handling Approach |
|---|---|---|
| **Failed login** | Generic "Incorrect email or password" — never reveal which field was wrong. | Return 401, log attempt (email hashed/redacted in logs where reasonable), apply rate limiting after repeated failures. |
| **Network failure** (general) | Non-blocking banner: "You're offline — some features are unavailable right now," listing what still works. | Retry with backoff for idempotent requests; queue non-idempotent actions (upload) via WorkManager; surface a clear error rather than an infinite spinner. |
| **PDF upload failure** | "Upload didn't go through. Check your connection and try again." with a retry button. | Client retries via WorkManager on connectivity restore; server returns specific status codes (413/415/422) mapped to distinct client messages where the cause is known. |
| **Invalid PDF** (wrong type / scanned / too large) | Specific message per cause: "This file isn't a PDF," "This looks like a scanned document — text-based PDFs are supported for now," "This file is too large (max 50MB)." | Server-side validation stage rejects with a categorized reason (`PDF-PROCESSING.md`); client maps reason code to the specific copy above rather than a generic failure. |
| **AI failure** (provider error/timeout during topic extraction or analysis) | "We couldn't process this material right now. You can try again." | `AIService` call wrapped with timeout + limited retry; failure sets `StudyMaterial.status = FAILED` with reason `ai_error`; error detail logged server-side, never surfaced raw to client. **Phase 8 QA fix**: prior to this phase, `MaterialService.upload_and_process`'s per-chunk `embed_text` call was NOT wrapped in any exception handling — a raised exception (e.g. a real `OpenAICompatibleProvider` failure) would propagate as an unhandled 500 instead of the documented `FAILED`/`ai_error` outcome. Now wrapped in `try/except`, rolls back any partially-created topics/units, and sets `FAILED`/`ai_error` as documented. Covered by `tests/test_materials.py::test_upload_marks_ai_error_on_embedding_failure`. |
| **Quiz generation failure** (insufficient grounding material, provider error, validation stripped too many questions) | "We couldn't build a fair quiz on this topic yet — try studying a bit more or picking a different topic." | Generation service retries once with adjusted parameters; on persistent failure, returns a specific error code the client maps to the message above; break remains in `BREAK_VERIFICATION`, not silently stuck. |
| **Permission denial** (Usage Access, Notifications, etc.) | Calm, specific explanation of what won't work and how to enable it later, never a repeated nag dialog. | Client checks permission state before relying on a feature; gracefully disables just that feature's UI affordance rather than crashing or blocking unrelated flows. |
| **Background service failure** (foreground service killed by OS) | No direct user-facing error — session state is simply recovered transparently on next check. | WorkManager watchdog detects the mismatch (active session, no running service) and restarts the service; state recomputed from Room per `FOCUS-ENGINE.md`. |
| **DB errors** (backend) | "Something went wrong on our end. Please try again in a moment." | Transaction rolled back; 500 returned with a correlation id; full error logged server-side (never raw SQL/stack trace to client) per `SECURITY.md`. |
| **Expired session** (access + refresh token both invalid/expired) | "Your session expired — please sign in again." Any in-progress local focus session data is preserved and will sync once signed back in. | Client clears stored tokens, routes to Login; local Room session/quiz data is retained and queued for sync post-login rather than discarded. |
| **Notification failure** (permission denied or channel blocked) | No error dialog — the app simply notes in Settings that notifications are off, and relevant screens rely on in-app state instead of assuming the notification was seen. | Client checks `NotificationManagerCompat.areNotificationsEnabled()` before relying on a notification as the sole signal for a time-sensitive event; falls back to in-app banners when the app is foregrounded. |
